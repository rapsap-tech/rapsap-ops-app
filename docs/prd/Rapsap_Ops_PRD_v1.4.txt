What is the Operations App The Operations App ( rapsap. ops ) is one internal phone app (a PWA first, native Android and /iPhone apps later) plus an admin panel on the computer, used to run Rapsap's 10 stores day to day. It replaces the store WhatsApp groups that are used today for the daily checklist, sales reports (DSR) and team communication. In one line: staff do their checklist tasks with photo proof, store managers check the work and post sales, and HO sees every store live. What it does in Phase 1 • Daily Checklist : 47 timed tasks per store per day, each done with a photo taken in the app. • Sales (DSR) : the store manager uploads the day's DSR Excel; the app shows target vs achieved and trends. • Chat : WhatsApp-style store groups, with photos posted automatically and abuse/spam blocked. • Logins : phone number + OTP. Logins are created by the store manager (for staff) and by Admin (for store managers). • Admin panel : HO sees all stores, reviews checklist reports, manages logins and the checklist master list. A separate Operations platform (Recommended)/ Our current admin panel is built for the customer app (orders, catalogue, delivery). Store operations is a different job, and it will keep growing: after the checklist and DSR come accounts, sales, HRMS, role management, access management and more. We suggest building Operations as its own platform , separate from the customer admin panel: its own app, its own admin panel and its own backend, with a shared core (login, people, roles and access) that every future module plugs into. This keeps the customer system safe from Ops changes and lets Ops grow module by module. A suggested design is in section 6; the dev team has the final call. Who uses it • Staff in the store (cashier, housekeeping, security, FNV, ASM and others). • Store Managers (SM) , one per store. • Admin (HO) . In Phase 2, HO teams: B&M, HR, IT/Admin, Accounts, Cluster Ops. ↑ Back to index Page 3 of 50 =====PAGE rapsap. ops · Product Requirement Document · v1.4 2. Why we are doing this Today every store runs on WhatsApp groups. We analysed the export of a store WhatsApp group (1,806 messages). What we found: What we see today Why it hurts 26% of all messages are DSR posts (screenshots of sales). Sales are hard to compare across days or stores. Nobody can see a trend. 68% of DSR posts arrive after 11 PM. HO gets the day's numbers late, often next morning. Checklist proof is a photo dropped in a busy group. No way to tell if a photo is new, from the gallery, or for which task. Missed tasks go unnoticed. Stock-outs, damage, store issues and HO tasks are mixed in the same chat. Requests get buried. No owner, no status, no follow-up. Passwords and login details were posted in the group. Security risk: anyone in the group, including ex-staff, can see them. Abusive messages and forwards appear in work groups. No moderation, no record. What changes with the app • Every task has an owner, a deadline and a photo taken in the app with a time stamp. • The SM verifies work the same day; HO sees what is done and missed, live. • DSR is uploaded as a file, checked, and turned into charts and a clean snapshot. • Photos still reach the store group automatically, so the habit staff have today (click and post) stays, but it is now tracked. • Logins are personal and switched off when someone leaves. ↑ Back to index Page 4 of 50 =====PAGE rapsap. ops · Product Requirement Document · v1.4 3. Suggested architecture (Recommended) This is a suggestion for discussion, not a fixed design. The dev team knows the current systems best and should confirm, change or propose a better option. The aim is a base that can take many more modules without a rewrite. Figure 3. Suggested architecture: separate Ops platform with a shared core and plug-in modules Main ideas • Separate from the customer system. Ops gets its own backend and its own database. The customer app and current admin panel stay as they are. The only link is a sync of the store list. • One shared core, built once. Login, people and stores, roles and access, notifications, /files, chat, audit log and scheduler. Every module uses these instead of building its own. • Modules plug into the core. Daily Checklist and DSR first. Stock-outs, issues, damage, HO tasks, shrinkage next. Accounts, HRMS and sales analytics later. Each module owns its own tables. • One backend to start (a modular monolith). Easier to build, test and run with a small team. A module is split into its own service only if it grows large (for example chat or accounts). • Roles and access are data, not code. Admin can create a new role and choose its permissions per module and per store, without a release. This is the start of role and access management.
